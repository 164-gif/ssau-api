# План покрытия API

## Что значит «все API»

Абсолютно подтвердить отсутствие неописанных, закрытых или неиспользуемых API только по публичным страницам нельзя. В этом проекте полнота будет означать: систематически просмотрены публично доступные официальные веб-интерфейсы Самарского университета и связанные пользовательские системы; каждый реально наблюдавшийся HTTP-маршрут проверен отдельным запросом и записан с источником и границами доступа.

Поддомены и системы сначала фиксируются как **кандидаты**. Наличие сайта, HTML-страницы, JavaScript-файла или серверного маршрута само по себе ещё не подтверждает API.

## Очередь работ

1. Проверить карты сайта, `robots.txt`, публичные страницы и официальные API-документы основного домена. `robots.txt` открыт и не содержит запретов; `/sitemap.xml` на момент проверки отвечает 404.
2. Для публичных интерактивных разделов выполнять ограниченные браузерные захваты запросов, исключая аналитику и сторонние ресурсы. Просмотрены главная, новости, расписание, страница расписания факультета, каталог сотрудников и его фильтр. Эти захваты не показали отдельный first-party data API; публичный поиск групп найден POST-запросом из клиентского кода и отдельно проверен.
3. Исследовать расписание: публичные страницы возвращают HTML, поиск групп выполняется через `POST /rasp/search`, а расписание студента доступно через endpoint личного кабинета, обнаруженный в существующем клиенте. Последний не live-проверен с авторизованной сессией.
4. Проверить на приёмном сайте другие степени обучения и варианты карточек; два публичных маршрута уже найдены, карточка программы доступна в API Anything только через фильтр заголовка. Учитывать, что `repo.ssau.ru/jspui/robots.txt` запрещает обход `/discover` и `/simple-search`; не обходить эти разделы рекурсивно.
5. Для журналов проверить OAI-PMH для остальных журналов; `GetRecord` пока использовать через отдельный контекст журнала, так как общий endpoint возвращает `badArgument` для выданного им ID. Не выгружать большие корпуса без необходимости.
6. Для WordPress отдельно классифицировать GET-маршруты по публичной доступности и помечать изменяющие методы; не запускать POST/PUT/PATCH/DELETE.
7. Закрытые личные кабинеты оставить как отдельную область с явным требованием разрешённого тестового аккаунта; не сохранять cookies и персональные ответы.
8. Для каждого кандидата фиксировать результат: найдено, не найдено на проверенных страницах, недоступно, либо не исследовано. «Не найдено» не трактовать как доказательство отсутствия.

## Критерии подтверждённого API

- Зафиксированы метод, URL и тип контента из документации или запроса фронтенда.
- Запрос повторён отдельно с безопасными публичными параметрами.
- Записаны параметры, формат результата, требования к входу и дата проверки.
- Примеры не содержат персональных данных, секретов или живых сессионных значений.
- Запросы, меняющие данные, не запускаются без отдельного разрешения; каталог сейчас read-only.
